# 明确短指令即时执行设计

## 目标

语音控制开启后，只要浏览器的临时转写已经构成一条明确、完整的短指令，就立即提交解析并执行，不等待 Web Speech API 把结果标记为最终文本。监听会持续运行，直到用户主动点击关闭。

## 根因

当前 `useBrowserSpeechRecognition` 只允许暂停、继续和准备完成等少量临时转写即时触发。“快一点”“慢一点”等指令只能等最终转写，因此执行存在明显延迟，某些浏览器持续监听时甚至长时间不产生最终结果。

## 即时触发规则

前端维护一组只匹配完整文本的短指令规则，覆盖：

- 暂停、继续、准备完成。
- 快一点、慢一点。
- 指定倍速。
- 倒回或快进指定秒数。
- 重新播放。
- 上一个、重复当前、下一个动作。
- 从头开始教学。
- 开始录制、停止录制。

匹配前移除空白和常见中英文标点。固定短语使用完整匹配；带倍速或秒数的命令使用限制格式的完整匹配。普通对话、未说完的句子和仅包含关键词的长句不即时触发，仍等待最终转写后交给现有后端解析器。

## 防重复

即时触发继续走现有 `dispatchRecognizedTranscript`：

- 临时转写触发后记录规范化文本和时间。
- 2.5 秒内到达的相同或包含关系的最终转写被视为重复，不再次提交。
- 超过防重复窗口后再次说出相同指令，可以正常再次执行。

持续监听、自动重启和关闭行为保持不变。

## 代码边界

- 将 `isUrgentInterimCommand` 改为更准确的即时短指令判断。
- 把文本规范化和即时判断提取为可独立测试的纯函数。
- `useBrowserSpeechRecognition` 使用该函数决定是否提前分发临时转写。
- 不修改后端关键词规则、API 协议、语音控制界面或教学运行时。

## 测试

- “快一点”和“慢一点”即时匹配。
- 暂停、继续、动作切换、录制等明确短指令即时匹配。
- “调到 0.5 倍”和“倒回 5 秒”等参数化短指令即时匹配。
- 普通句子、关键词片段和未完成的参数化指令不即时匹配。
- 现有去重逻辑继续阻止临时结果和最终结果重复执行。
- 前端 lint 和生产构建通过。
